# matchwatch: notes for whoever works on this next

matchwatch runs on an OpenWrt router and judges each online match: the game server, the route to it, the player's own line and their PC. It works from packet timing only and never alters game traffic. Version 0.39.0.

## Layout

- `files/matchwatch`: the CLI and service (POSIX sh for BusyBox ash). Capture, probes, blocking, stay mode, lobby alert, share files, QoSmate check and fix, and `_action`, which runs the dashboard's buttons.
- `files/analyze.awk`: the engine. Reads `tcpdump -tt -n -q -l` lines plus `TICK` heartbeats, tracks flows, scores sessions, writes history and per-match detail JSON.
- `files/report.awk`: every report and JSON export built from `sessions.tsv` (history, servers, datacentres, regions, stay lookups, hours, recap, games).
- `files/matchwatch.config`: default settings, installed as `/etc/config/matchwatch`. The script's own defaults cover anything missing.
- `files/public.html`: shell page for the optional dashboard without login.
- `files/geofeeds.list`: hosting companies' published address-range lists (RFC 8805 geofeeds), used by stay mode.
- `files/*.list`: Vultr region ping hosts, countries and areas for stay mode, game labels by port.
- `luci-app-matchwatch/htdocs/luci-static/resources/matchwatch/dashboard.js` and `.css`: the dashboard, vanilla JS, hash routes (Live, Last match, Matches, Servers, Tools). One copy, two homes. Whoever hosts it passes in how to talk to the router (`T.get`, `T.act`), and it draws inside a shadow root so the LuCI theme and the dashboard cannot disturb each other's styling.
- `luci-app-matchwatch/htdocs/luci-static/resources/view/matchwatch/`: the LuCI pages. `dashboard.js` hosts the dashboard, reading data with `file.read` and running buttons through rpcd. `settings.js` is a native form on `/etc/config/matchwatch`.
- `luci-app-matchwatch/root/`: menu entry (Services, MatchWatch), permissions (`acl.d`), and the rpcd backend `luci.matchwatch` with two methods, `read` and `write`, so permissions can tell looking from changing. It calls `matchwatch _action`.
- `packs/`: community share files (game packs) and the format and acceptance rules for them. Not installed; people import what they choose.
- `build.py`: bundles both directories into `dist/matchwatch-install.sh` (heredocs) and writes `dist/version` (the version and the installer's SHA-256). Run it after any change to either, and commit both: routers update from them.
- `test/`: traffic generator, stand-ins for router tools, a test site serving the view-only dashboard, Playwright screenshots. `test/mockshots.py` makes `docs/*.png` from invented data with headless Edge or Chrome and Pillow; it needs no router or BusyBox.
- Privacy: the repository is public. Nothing from a real network goes in it: no real LAN, ISP or game server addresses, device names, match history or screenshots of real data. Tests and screenshots use the documentation ranges 192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24. Commit with a GitHub no-reply address.

On the router: `/usr/bin/matchwatch`, `/usr/lib/matchwatch/`, `/etc/config/matchwatch` (settings), `/etc/matchwatch/` (`sessions.tsv`, `matches/*.json`, blocklist, stay, `games.local`, `regions.local`, `ratings.shared`, `favourites`, `share.undo/`), `/tmp/matchwatch/` (runtime; `www/` holds the JSON the dashboard reads), the LuCI files under `/www/luci-static/resources/` and `/usr/share/`. With the no-login page on, the service also creates `/www/matchwatch/` and `/www/cgi-bin/matchwatch-mark` at start, and removes them when it is off.

Settings: the script reads `/etc/config/matchwatch` through `config_get`. With `MW_CONF` set it sources that shell file instead, which is how the tests run it off-router. Versions before 0.10.0 kept settings in `/etc/matchwatch/config`; `matchwatch _migrate` (run by the init script) carries them over once and renames the file to `config.imported`. Saving in LuCI fires the init script's reload trigger, which restarts the service.

Slow tools: an rpcd call must answer within seconds, so the line test and route trace start in the background, print a job number, and write `linetest.json` or `trace.json` into `/tmp/matchwatch/www/`. The dashboard's `job()` polls that file until its `id` matches. Follow the same pattern for anything that takes more than a few seconds.

Share files (`matchwatch share export|check|import|undo|forget`, 0.14.0): one text file, first line `matchwatch-share 1`, sections `[games]` `[regions]` `[places]` `[ratings]` `[settings]` `[favourites]`. A favourites line is `server|game|city|cc|host|rating|matches|lat|lon`; `report.awk` MODE `share_servers` writes them. Two extra names are not sections: `allservers` (export every server as a candidate, with a tenth field marking favourites, for the dashboard's picker) and `favplaces` (import: add the cities of the file's favourite servers to the stay pool). `share_load` checks every line in one awk pass and writes the good ones to a temp folder; import then merges them into `games.local`, `regions.local`, `stay`, `ratings.shared` and the settings, after copying the old files to `share.undo/`. From the dashboard the file's text travels as the `data` argument of the rpcd `write` method and reaches `_action` on standard input. Unknown sections are skipped, so later versions can add some. Choosing single items to share is done in the dashboard only (`sharePicker`): it asks for the full export, shows a tick per line, and builds the file text in the browser.

Favourites (0.15.0): `/etc/matchwatch/favourites` holds one server per line: the address, then for ones taken from a share file the game, city, country and host, tab separated (`matchwatch fav add|remove`, actions `fav`/`unfav`). `cmd_block` refuses an automatic block of a favourite, and the lobby message names one. Grouping by game is done in the dashboard from the match history, falling back to the game stored with an imported favourite (`gameOf`).

Servers page (0.29.0): four tabs like the Tools page (`SERVTABS`, addresses `#/servers/<tab>`): Where I play (staying banner, map, one list of everything let in, the text box, how each game is filtered), Favourites, Servers (servers, blocks, datacentres), Regions and games. It had grown to ten sections and 4,500 pixels. `brief(text)` shows a long note as its first sentence with the rest behind More; write notes so the first sentence stands alone. The Live page lists three getting-started steps until there is a match on file. On a coarse pointer a circle is drawn with two taps. The mock page now has a viewport tag, without which phone-width checks silently render at 980 pixels.

Dashboard look (0.15.0): colours and radii are variables at the top of `dashboard.css`; the chart reads the same variables. Buttons are a quiet fill (`--soft`), `solid` for the main action, `danger` for destructive ones. The Tools page is four tabs (`TOOLTABS`, addresses `#/tools/<tab>`) of rows built by `tool(title, description, controls...)`: say what a tool does on the left, put its control and result on the right. Check both themes after a style change (`dark:` in the mock page of `test/mockshots.py`).

Removing (0.17.0): `cmd_forget match|server|dc` rewrites `sessions.tsv` without the chosen rows, deletes their `matches/<start>.json`, re-exports, and restarts the engine only when no match is in progress (its ratings live in memory). It refuses a favourite server, and a datacentre holding one. Actions `forgetmatch`, `forgetserver`, `forgetdc`.

QoSmate match record (0.18.0): `qm_loop` (started by `_probe_start`) saves cake's per-queue counters from `tc -s qdisc` for the WAN port and `ifb-<wan>` at match start and tracks the peak `pk_delay` every five seconds; `qm_sum` (in `_probe_stop`) writes the differences as one line of JSON, `qm.json`, which the engine copies into the match detail as `qm`. The last column of cake's table is taken as the top queue. Read only. Proven on cake diffserv3 only; nothing is written in HFSC mode.

Unnamed ports (0.18.0): a stream on a port with no label is kept only if at least 120 s were analysed and under 15% of updates were missing; otherwise it is dropped at `session_end`, logged, and listed in `skipped.json` with a reason. The 15% line comes from a single real example (a 42 s stream at 28%), so expect to tune it. No match-started alert is sent for an unnamed port.

Whole ranges (0.20.0): with stay mode on, `stay_ranges` (always started in the background; the first run does about forty city lookups) downloads the lists in `geofeeds.list` and `geofeeds.local` into `ranges.cache`, places each city with Open-Meteo (`cities.cache`), and loads every range outside the pool into the nftables set `away`. Two rules refuse UDP between `device_ip` and that set; `nft_ready` rebuilds the table when the device changes. `cmd_lobby` returns early for a server already in `away`. Seen on the router: the Vultr list downloads, the city lookup takes a country code, and an interval set with `auto-merge` accepts overlapping ranges. `ranges_cover` writes `coverage.json`: how many known ranges each place in the pool holds, and for a place with none the three nearest cities that have servers (`coverage.sug`, added with the `staysuggest` action; country centres come from `countries.list`). The owner chose a country with no servers and had no way to know. Not yet seen: whether the game then finds a match faster.

Where each game plays (0.21.0): `report.awk` MODE `gameplaces` groups game and /24 from `sessions.tsv`, from `tried` (written by `tried_note` in `cmd_lobby`: network, port, city, country, host, AS, position, count, last seen; 2,000 lines at most) and, for the dashboard only, from `gameplaces.shared` (imported, 5,000 lines at most). `ARG=share` prints your own for the `[gameservers]` share section; `ARG=json` writes `gameplaces.json` with an `in` flag when a stay pool is set. Shared entries never reach the `blocked` or `away` sets. `sessions.tsv` is trimmed to its newest 5,000 lines in `cmd_after`; the owner wants total storage well under 20 to 30 MB for small routers.

Updating (0.22.0): `matchwatch update` reads `dist/version` from the raw GitHub address of `main` and compares; `update now` (action `update`, a slow tool writing `update.json`) downloads the installer, refuses it unless its SHA-256 matches that line, and runs it. It refuses during a match. Nothing is fetched until the owner asks. Whatever is pushed to `main` in `dist/` is what every router installs, so never push a `dist/` that has not been installed on the test router first. The installer writes each file as `<name>.new` and moves it into place, because the updater runs from the script being replaced. `MW_UPDATE_URL` points it elsewhere for tests, with `MW_ROOT` so the installer writes into a sandbox.

Which game (0.32.0): the owner played a new Steam game and got no new-game prompt, because Steam's network (27000-27200) already has a label and every game on it looks the same from the router. `matchwatch matchgame <start> [name]` (action `matchgame`, the name in `name`) writes `matchgames` (start, name; newest 5,000) and `playing` (label, name, since, until; until 0 is for good), and `named()` in `report.awk` uses them: a match's own name first, then the label's standing name for matches that started after it was set and before it runs out, then the label. The owner was unsure how long a name should hold, so the dashboard asks: this match only, 1 day, 1 month or until changed (`days` carries the hours; 0 is this match only and nothing is for good). Since 0.34.0 the same box is offered for any named match behind a small "Wrong game?" link (`gameFix`), on the Live page and the match report, because a port alone can name the wrong game. There the default is this match only: a standing name is keyed by label, so renaming one Call of Duty match for a month would rename every match under that label. For a shared network the default is 1 day. Since 0.34.1 no match report shows the box until asked: the owner found it open on every Steam report too much, so reports carry only the inline link ("which game?", "wrong game?" or "change"); the Live page still shows the box outright for a shared-network match that has no name yet, and a link once it has. `report.awk` finds both files beside `games.local`. `history.json` carries `label` as well as `game`, and `hold.json` carries `as`, the standing name while it holds, and `until`. `status.json` carries each live session's `game` (the engine's `gamename`, which checks the host), and the Live page words it with `liveGame`: the label, the standing name, or "A Steam game". The dashboard asks on the Live page and the match report for labels `sharedLabel()` accepts ("Steam games..." and names with " or "). It renames only: `kindof`, the lobby check and strict still go by the label. Tested against the owner's history with invented Steam rows; not yet used on a real match.

Reasons and grades (0.22.1): the engine notes every deduction as it scores (`why_add`) and writes the largest one or two per part into the match detail as `why` (`server`, `route`, `line`, `pc`); the dashboard prints them under the four scores. Matches from before 0.22.1 have none. Change a scoring formula and its `why_add` line together, and the table in the README. Tests get letters in the dashboard only: `letter(score)` for the line test (`score` in `linetest.json`), `pingLetter(ms)` for a trace and the region table.

Single servers in the pool (0.23.0): `/etc/matchwatch/allow` holds exact addresses (`matchwatch allow add|remove`, actions `allow`/`unallow`, at most 100). The nftables set `allowed` is accepted at the top of the chain, before `blocked` and `away`, so the region lock itself is unchanged and an allowed server passes it. `cmd_lobby` skips the stay decision for one, an automatic block skips it, and blocking one by hand takes it out of the list. `nft_ready` rebuilds a table that has no `allowed` set. The owner chose exact addresses over /24s so nothing unvetted gets in; expect to revisit if games rarely offer the same address twice. Not yet seen on a real match. `servers.json` carries `in` (true, false, or null when the server cannot be placed or nothing is being stayed on); the dashboard shows "In your places" in place of Add to pool when it is true.

The map (0.24.0): `mapSection` on the Servers page. Leaflet 1.9.4 ships in the installer (`leaflet.js`, `leaflet.css`, unchanged; SHA-256 checked against the published integrity values when it was added). LuCI's own code lives in `window.L` and Leaflet claims the same name, so the dashboard fetches Leaflet's text, runs it, takes `window.L` and puts LuCI's back in the same breath (`leaflet()`); never load it with a script tag. The map element is built once and re-attached on every page redraw (`MAP.box`), and nothing is redrawn while a circle is being drawn or edited (`MAP.busy`). A circle is an ordinary line in `stay` (`matchwatch stay circle <lat> <lon> <km>`, `stay set <n> ...`; actions `staycircle` with `lat/lon/km` and `stayset` with `n/lat/lon/km`, because action arguments allow only digits, dots, slashes and hyphens). `info.json` carries `pool` with each place's geometry, and `servers.json`, `regions.json` and `gameplaces.json` carry `lat` and `lon`. Tiles come from OpenStreetMap, fetched by the browser. Leaflet's dragging throws on synthetic mouse events sent to `document`; test with real pointer input. Seen on the owner's router through the no-login page; drawing and editing were tested against invented data only.

Strict games (0.25.0, called hold in the code because `STAY_STRICT` was taken): `/etc/matchwatch/hold` lists game names (`matchwatch strict on|off <game>`, actions `holdon`/`holdoff` with the game in `name`). nftables gets `hold_ports` (those games' server ports, minus every voice label's ports) and `okay` (servers with a verdict), and one rule after the others: the device's UDP to a held port is dropped unless the server is in `okay`. The engine listens on the LAN side, so it still sees the dropped packet: `hold_seen` asks `matchwatch _hold <ip> <port>` on the first packet out, again every 4 s while nothing comes back, and stops once a reply is seen. `cmd_hold_check` lets through anything allowed, unplaceable, not labelled a game, or in the address block of a match in progress, and blocks the /24 of a game server outside the pool. `hold_apply` flushes both sets, writes `$RUN/hold.ports` (first line a serial; the engine drops its memory when it changes), waits two seconds so the engine has the ports first, then fills `hold_ports`; it runs on every pool change and at service start (six seconds after the engine). It must fail open: the init script's `stop_service` flushes `hold_ports`, and so does the start of `run`. A game is only offered when at least half its ports are left after voice ports are cut out (Roblox is not). Seen on the owner's router: the rule and sets in the live firewall, released on stop, back after start, fully undone. Not yet seen: a real new server being held and judged during matchmaking.

Match mode (0.30.0, off by default, `match_mode`): QoSmate's cake limit on during matches and lifted between them. `mm_set tight` runs `tc qdisc change dev <wan> root cake bandwidth <UPRATE>kbit` (and `ifb-<wan>` with `DOWNRATE`), `mm_set loose` runs `... cake unlimited`; note it is `cake unlimited`, not `bandwidth unlimited`, which tc rejects. A change keeps every other cake option and needs no QoSmate restart; QoSmate's uci settings are read and never written. Tight is asked for by `cmd_lobby` and `_probe_start`; `cmd_after` starts `mm_later`, which switches after `MM_HOLD` if no match or candidate is in `status.json` and no newer stamp has been written (`mm.stamp`). It must fail tight: `run` starts tight and lifts after a minute, the init script's `stop_service` calls `_mmstop`, and switching it off sets tight. `matchmode.json` carries the state for the Live page and the Tools row. Since 0.31.0 the owner chooses the speeds ("don't always auto decide for people"): `mm_on_down`, `mm_on_up` (while playing; empty follows QoSmate's own rate), `mm_off_down`, `mm_off_up` (between matches; empty is no limit) and `mm_hold` (seconds after a match before switching; 300 by default since 0.34.0: the owner first found a fixed five minutes too long, then, with a choice on offer, found a 30-second default too quick; 0 is at once, though never under three seconds so the engine has written that the match is over). `matchwatch matchmode speeds` and the action `matchmodeset` (`a/b/c/d[/hold]` in kbit) save them and put them to work at once. `mm_set` has three targets: `tight`, `loose` and `own`, the last being QoSmate's own rates, used on stop and off. The Tools row has a panel (`mmSpeeds`): a number box and a slider per speed, the slider in percent of QoSmate's own rate. Never trust `mm.state` alone (0.32.2): the owner ran a speed test between matches and got the limited speed, because QoSmate had been restarted overnight, which puts its own rates back, while `mm.state` still said `loose` and `mm_set loose` returned early. `mm_same` now reads the rate cake really has (`mm_actual`, from `tc qdisc show`), `mm_set` only skips when the queues agree, and the service runs `matchwatch _mmcheck` once a minute to set the speeds again when something outside has moved them. QoSmate's own speeds come from the queues (0.32.3, `mm_own`): a friend of the owner saw no speeds at all. QoSmate fills missing options from its defaults file and caps DOWNRATE at BWMAXRATIO times UPRATE, so `qosmate.settings.UPRATE/DOWNRATE` can be empty or differ from what is in force; a rate of 0 there means that direction is not shaped (no cake at all). `mm_own` reads `tc` whenever the queues are as QoSmate left them (no `mm.state`), remembers the answer in `/etc/matchwatch/mm.own`, learns again when `mm_check` sees an outside change, and falls back to uci last. `run` restores QoSmate's speeds first if `mm.state` survived an unclean stop. `mm_why` names the reason match mode cannot work (`noqos`, `disabled`, `notcake`, `autorate`, `noqueue`); QoSmate's autorate service rewrites the same bandwidth several times a second, so match mode refuses while it is on. QoSmate's port, not OpenWrt's (0.32.4, `qos_dev`, `QWAN`): the same friend then got "QoSmate has no speed limit on the internet port" with cake running. MatchWatch was looking at `WAN_IF` (what `network_find_wan` gives, `pppoe-wan` on a PPPoE line) while QoSmate shapes `qosmate.settings.WAN`, which can be the physical port underneath or the reverse. Everything that reads or changes QoSmate's queues (match mode, the per-match queue record, the priority check's counters) now uses `QWAN`: QoSmate's setting when that port exists, else `WAN_IF`; the downloads queue is `ifb-$QWAN`. Packet capture for the priority check stays on `WAN_IF`. Without QoSmate there is no match mode (0.38.6, the owner's call after `matchwatch matchmode` printed speeds of 0 kbit on a router without it): the command says it needs QoSmate and `speeds` refuses, and `matchmode.json` has `on` false and `state` off even when `match_mode` is 1 in the settings, so the Live page says nothing about it. The Tools row already showed the QoSmate notice instead of the controls. The Settings page still lists the tick box, labelled as needing QoSmate: hiding it would mean the LuCI view asking the router whether QoSmate is there, and that view is kept small. Cake modes only. The owner wants QoSmate credited: say that QoSmate does the prioritising wherever this is described. Seen on the owner's router: a full on, lifted, limits back, off cycle on the live queues, every cake option identical afterwards and QoSmate's settings untouched. Not yet seen: a real match switching it.

Ports (0.33.0): `ports_check` tests the three ports and prints `ok`, `note` or `WARN` lines, each saying where to correct it: `LAN_IF` (must exist; with a device chosen, must be the port `ip route get <device>` names), `WAN_IF` (must exist and be the default route's port), and `QWAN` (QoSmate's setting must name a real port with a cake, hfsc or htb queue on it). `cmd_doctor` prints them, `info.json` carries `lan_if`, `wan_if`, `qos_if` and `port_warn` (the warnings joined), the Tools page shows `port_warn` as a banner on every tab and lists the ports under Settings in use. The owner asked whether to add a port picker: no for QoSmate's port, because a second setting that can disagree with QoSmate's is what caused the bug; the LAN and WAN fields under Settings, Advanced, already exist for the other two. Tested in a sandbox and on the owner's router; the warnings themselves only against invented cases.

The overlay, second design (0.38.2): the owner did not take to the pill of three lights and asked to see a redesign before anything changed. Four mock-ups later they chose a compact bar: place and game, ping, then the four areas in two rows of two, each with a light, a line of its last minute that changes colour, and marks underneath that stay (green a blip, amber felt, red bad). `status.json` now carries `near`, `navg`, `pavg` and `tl_n` (the ISP's first hop, live, from the probe's `near.last`, on the same seconds as `tl_p`), which is what lets it tell line from route. Per second and per area `ovPaint` works out a severity 0 to 3: line from `tl_n` over its average (4, 8, 20 ms), route from `tl_p - tl_n` over its median (5, 10, 25), server from `tl_d` (15, 40, 100), PC from `tl_u` (25, 50, 100); a second already explained by the line is not also charged to the route, nor one explained by either to the server. The light is the worst of the last five seconds. Each of the four areas can be left out too (`&areas=server,route,pc`), which the owner asked for so that someone whose ISP's first hop answers no pings can drop the Line row; with one or two areas the grid is a single column. Every part is optional and travels in the address (`#/overlay?show=place,game,ping,lights,lines,marks,rate,time&size=s|m|l&idle=0`; `route()` parses it into `OVQ`), and the Tools row builds the address from tick boxes. The bar is sized in em, so the three sizes are one font-size. The owner's first OBS test (0.38.3) showed Server amber with a mark every second through a clean match while the Live page beside it showed nothing wrong: `tl_d` and `tl_u` are the longest gap in each second, not lateness, so a server sending 21 updates a second reads 48 ms when all is well, and the overlay had judged the raw figure. It now does what `drawChart` does: takes the median away first and calls a second felt above `max(30, median)` for the server and above 100 ms for the PC (a blip at half that, bad at 100 and 200), and the line's own steps went up to 8, 15 and 30 ms because the ISP's first hop answers pings unevenly. The picture of a match and the network section had the same fault and the same correction. Anything new that reads `tl_d` or `tl_u` must subtract the normal beat. The live split has never been checked against a real rough match and its lines are first guesses; the match report stays the final word. Show the owner a design before building a look they have to live with.

The README (0.38.1): the owner asked for it to be redone with fewer, better pictures once those three were in. It now opens with what you get, one short section and one picture per thing, and the manual follows unchanged. `test/mockshots.py` makes eight pictures and no others (`match-report`, `live`, `overlay`, `card`, `network`, `map`, `pingrange`, `tools`); `?shot=card` and `?shot=net` in the mock page show the shareable picture and the network section on their own. Add a picture only for a feature worth a section at the top.

Three more the owner took together (0.38.0), asked for as a "halo feature". Early warning: `rough_early` in the engine looks once at a game-labelled session when `EARLYS` (30) seconds have been analysed, and only speaks when it is clearly rough: 3% of updates missing, 8% late, two freezes, or half its windows rough. It prints `EARLY`, puts `early` on the session in `status.json` (the Live page adds a red line; the overlay a fourth light) and runs `matchwatch _early <ip> '<reason>'`, which logs and sends one short line to the phone (`early_warn` 0 stops the phone line; no LuCI field). The lines are first guesses set high, because a false alarm costs a good match; tune them against real rough matches. Not yet seen on a real match. The overlay: the address `#/overlay` draws only a strip (`pageOverlay`, `ovPaint`, repainted from `setState` every second) with three lights, each the worst of the last five seconds of `tl_d` (server and route together: which of the two is only known when the match ends), the ping against the median of `tl_p`, and `tl_u` (the PC). The page and body backgrounds are made transparent for an OBS browser source. It is reached through the no-login page; the Tools page shows the address. The proof card: `proofCard(m)` draws a 1200 by 630 canvas in the browser (overall score, verdict, the four parts, `tl_d` as bars) with the game, place and time and no address, and `cardBtn` saves it as a PNG. Nothing is uploaded.

Three things the owner chose from a list of what would help most (0.37.0).

The network during a match: `net_on` adds a chain of its own, `netcount` (forward hook, priority -6), to the `inet matchwatch` table with two dynamic sets that carry a counter per element, `netup` (by source, packets coming in on `LAN_IF`) and `netdn` (by destination, going out on it), and two named counters for all IPv6 together. `net_loop` (started by `_probe_start`) reads them every five seconds and logs any address that moved 200 kbit or more; `net_sum` (in `_probe_stop`) writes `net.json`: the six busiest devices that reached 2 Mbit down or 0.5 Mbit up, each as a row of Mbit per sample with the name from `/tmp/dhcp.leases`; the engine copies it into the match detail as `net`. `net_off` removes the chain and sets when no other match is being recorded, and `run` and `stop_children` remove them outright. Nothing is counted between matches. The verdict is worked out in the dashboard (`netBlock`): for each device, the mean of `tl_d` and `tl_p` over its busy samples against its quiet ones, called worse only at 5 ms and half as much again (30% for ping), and said to be the same otherwise. It changes no score. Bytes are kept as strings in awk until subtracted, because BusyBox awk prints large numbers in exponent form. `net_watch` 0 switches it off (no LuCI field). With `flow_offloading` on, `net.json` carries `why: offload` and the report says the figures are incomplete. Device names are in match detail, which the no-login page can read; they never leave the router. Seen on the owner's router: the chain counting real traffic for forty seconds, a test download from the gaming PC recorded at the right moment, and the table as it was afterwards. Not yet seen: a real match with another device busy.

## Rules that have bitten already

- After the first real update the owner saw the old dashboard until logging out and in: the browser kept its stored `dashboard.js` and `.css`, whose addresses never changed. Now the LuCI view and the no-login page ask for both with `?v=<version>`, and the dashboard compares its own `BUILT` with `info.json`'s version every fetch; on a difference it refetches its files with `cache: "reload"` and reloads once (`versionSeen`, guarded by `sessionStorage`). Bump `BUILT` with `VERSION`; `build.py` refuses to build otherwise. The LuCI view file itself is loaded by LuCI and cannot be stamped, so keep it small and change it rarely.
- The dashboard fetches everything every fifteen seconds but redraws a page only when the data has changed (`sigNow`). Redrawing regardless made the Servers page flicker, and a block filled in by a later fetch shifted everything under it. Anything a page shows must be loaded in `loadAll`, not fetched inside the page function.
- The `blocked` set applies to every device, which is fine for single servers. Whole ranges from a hosting company must never go in it: they hold ordinary web sites. They go in `away`, which only refuses the gaming device's UDP, and nothing wider than a /12 or in private space is taken from a list.
- A range whose city cannot be placed is left alone when the pool has a city in it. Guessing would block the wrong region.

- Phone alerts are one short line with no addresses or host names; the full sentence goes to the log and the dashboard. The owner found five long turn-away alerts in a minute too much: a stay-mode turn-away only reaches the phone on `lobby_alert` 2, and lobby alerts are limited to one a minute.
- In `cmd_lobby` the stay decision comes before any ping or traceroute. Measuring first let the game join the server and then threw the player out.
- `stay_apply` keeps the stay blocks that are still outside the pool (placed by `geo.cache`). It once rebuilt them from the match history alone, which dropped every block made as the game tried a server never played on; changing the pool then let the game straight onto one of those.
- `stay_apply` never blocks the address block of a match in progress (read from `status.json`); `cmd_after` applies it once the match has ended.

- BusyBox awk only. No `cos`, `sqrt` or other maths functions (some builds lack them), no gawk extensions. Distances are compared squared with a cosine series.
- A sum in the shell on a value read from a file (`$(( now - $(cat file) ))`) ends the whole script when the value is not a number, and in `run` or `cmd_after` that is the service or the export after a match. Pass such values through `mm_num` first (0.38.5 did so for the block list's end times, `regions.tsv`, the lock and busy files and `update.seen`); `fill_blocklist` skips a line whose end time is not a number. None of these was seen to happen.
- A sweep worth repeating after large changes (0.38.5): put a script called `awk` first on `PATH` that runs gawk and logs its standard error, replay the `gen.py` scenarios into a sandbox `DATA` with the engine patched to write history, run every command and `_export`, then load every JSON file with Python. gawk stops on faults BusyBox awk passes over (too few values for a format). Do not use `gawk --lint`: version 5.3 dies of an internal error in it. The sweep of 0.38.5 ran 58 commands and found nothing beyond the `regions_json` fault.
- BusyBox ash only. No bashisms. Test with `busybox ash -n` and `busybox awk`.
- Game traffic is the ground truth. Probe results (ping, traceroute-style UDP) only split blame; they never lower a score when the game's own packets arrived cleanly. Servers ration UDP probe replies, so unanswered ones are not loss.
- Scoring starts when steady traffic begins (`session_start` resets the accumulators). Games often handshake, wait about 30 s, then start the stream.
- PC send rate follows frame rate, so only pauses over 100 ms are scored for the PC.
- tcpdump on the WAN port sees packets after the qdisc, so cake's `wash` shows DSCP 0. The QoSmate check relies on queue counters first.
- Voice chat must never be cut off. Stay mode, the lobby alert and auto-block act only on servers labelled as a game in `games.list` or `games.local` (`kindof`/`isgame` in the engine, `which_label`/`is_game_port` in reports). Voice streams (`kind` = `voice`) are not tracked at all: no session, no probes, no alerts. Unlabelled ports are tracked and rated but never blocked. `games.local` is read first, so naming a port or range makes it a game. The engine re-reads both files every 20 ticks.
- Labels are `name|ports|kind|hosts`, first match wins. `hosts` are words looked for in the server's isp, org and AS name; a label with hosts only matches once the lookup is in `geo.cache` (the engine asks with `matchwatch _geo <ip>`), and until then the stream falls through to later labels. This exists because ports overlap badly: Roblox and Discord voice share 50000-65535, Valorant sits inside Rocket League's range, Apex inside Call of Duty's. Reports only have org and the AS number, so give host-checked labels the AS number too (`roblox,as22697`). Put narrow and host-checked lines above wide ones. Never add a wide range without a host check: it turns every unknown stream in that range into a "game" that stay mode may block.
- Publishers' port lists mostly do not say whether a port is the server's or the player's, and many are missing. `games.list` marks lines without a publisher source as unconfirmed. Do not add a game from memory; find a source.
- The lobby alert needs a game-labelled port and one of two more things: the matching label is host-checked and the server's host matches (`hostgame`, since 0.28.0, at the owner's request so filtering works from a game's first server as Geomate's does), or the port or /24 carried an earlier match (`KPORT`, `K24`). Never drop the second test for labels known by port alone: game port ranges are wide (30000-45000), and calls and peer-to-peer traffic use ports inside them, so with stay mode on that would block non-game servers. A patch once dropped it for everything. While a host lookup is pending the check is put off (`hostpending`, up to 400 packets) rather than decided on a later port-only label. A port-only server left alone this way is passed to `matchwatch _unseen` (0.28.1), which blocks nothing: if the server is outside the pool it writes a `lobby.json` with `strictname`, so the Live page says it was let through and offers to make that game strict. A match played on a server outside the pool carries `outside` in its detail (`allowed`, `port`, `host` or `unnamed`, worked out in `_probe_stop`), and the report opens with why it was not turned away (0.28.2). The pictures use real game titles with the ports from `games.list`, at the owner's request; hosts and addresses stay invented.
- Share files come from strangers. Import must never be able to block a server or widen what counts as a game without a check: ratings from others are display only (`ratings.shared` is never read by auto-block or stay mode), a game label over 2000 ports wide needs hosts, host words need three characters, settings are a fixed list of numeric keys with ranges (never `autoblock`, `ntfy_url`, `device_ip`, `only_filter`), and region hosts must be names, not addresses. Export must never include the device, LAN or ISP addresses, or match times.
- `matchwatch game name <port or lo-hi> <name> [hosts] [voice]` and `game remove` are the only writers of hand-made labels (actions `gamename`, where `region` carries the host words and `days` = 1 means not a game, and `gamedel`). They refuse a range over 2000 ports with no host words, the same rule as imports.
- A name given by hand goes at the top of `games.local` so it beats an imported label covering the same port; imported labels are appended.
- A patch script once emptied `files/matchwatch` by opening it for writing before reading. Check file sizes after scripted edits.
- Python run from a Git Bash heredoc turns `\\n` inside its strings into real newlines. Write patch scripts to a file and run the file.
- Unix line endings everywhere. On Windows, Python writes CRLF by default and Git for Windows checks files out with CRLF; either breaks every script on the router. `.gitattributes` forces LF and `build.py` writes LF. To count carriage returns in Git Bash use `tr -cd '\r' < file | wc -c`: `grep -c $'\r'` there matches every line, which once made clean files look broken.
- The NAT check and the speed advice answered "unknown action" in the owner's browser on the day they shipped (fixed in 0.37.1). Which rpcd method a button uses is decided in the LuCI view (`READS` in `view/matchwatch/dashboard.js`), a second list beside `READ` in the rpcd backend, and the two new actions were only in the backend's. Testing with `ubus call luci.matchwatch read` went straight past the view and passed. The backend's `write` method now accepts the read actions too, so a missing entry, or a browser holding an old copy of the view, no longer breaks a button; still add a new looking action to both lists, and test a new button through `write` as well as `read`.
- A LuCI session gets its permissions at login. After installing the app, an already logged-in browser must log out and in before Services, MatchWatch appears or its buttons work.
- The router's BusyBox `nc` has no `-l` or `-w`, and `uclient-fetch --post-data` sends chunked bodies. To exercise the backend from the router's shell use `ubus call luci.matchwatch read '{"action":"doctor"}'`.
